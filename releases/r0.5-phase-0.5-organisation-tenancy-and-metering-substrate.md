## Goal

Add `organisation_id` scoping to every substrate storage primitive and implement substrate-level metering of resource consumption (tokens, invocations, storage bytes, execution wall-clock, cross-workspace traversals). This release establishes the tenancy boundary that the [Structured Governance Taxonomy](https://oraclous.atlassian.net/wiki/spaces/OP/pages/688439) policy sets bind to (via `owner_organization`) and the metering surface that the optional cloud-mode Billing Service later consumes. Both are cloud-mode prerequisites and must land at the data layer before any service reorganisation, because adding tenancy retroactively across many services is harder by an order of magnitude than adding it once at the substrate.

## Scope

### In scope

* `organisation_id` column or property added to every Neo4j node, Neo4j relationship, Postgres table, Redis key prefix, cache entry, and search index
* Every query and write path extended to include `organisation_id` as a mandatory filter, sourced from authenticated context (never from request body)
* The three existing multi-tenant component wrappers (`MultiTenantVectorRetriever`, `MultiTenantHybridRetriever`, `MultiTenantVectorCypherRetriever`) extended with an outer organisation-scoping layer
* Multi-tenant isolation test suite (`test_multi_tenant_isolation.py`) extended with organisation boundary tests covering cross-org read denial, cross-org write denial, cross-org Cypher traversal denial, cross-org search denial, and cross-org cache miss
* Metering subsystem implemented at substrate level: LLM tokens, tool invocations, storage bytes, execution wall-clock time, cross-workspace traversal counts and bytes
* Metering write hooks added at the harness runtime, the capability registry resolution path, and the substrate write path
* Usage reporting API exposing organisation-scoped metering aggregates, ReBAC-gated to organisation admins
* Migration script for existing deployments: adds `organisation_id` to all existing data, defaulting to a single seed organisation per existing deployment
* Compliance work begins in parallel: ISO 27001 and SOC 2 Type II audit firm engagement initiated (the compliance work runs on its own track and is captured separately by the R-Compliance release)

### Out of scope

* Any service reorganisation (decomposition of `knowledge-graph-builder`, lifting of `AgentExecutor`) - these happen in R3 and R4
* Agent identity issuance and delegated identity tokens - R1
* Billing Service deployment - deferred to a future release; pricing model is product strategy and the metering surface from this release is the contract billing later consumes
* _HTTP usage-reporting endpoint_ — R0.5 ships only the substrate-level aggregation query primitive for usage reporting (ReBAC-gated to organisation admins). The customer-facing HTTP endpoint is deferred to **R6 (Application Gateway extraction)**, per [ADR-009](https://oraclous.atlassian.net/wiki/spaces/OP/pages/393423) (customers read their organisation's usage stream through the gateway).
* Self-hosted chargeback tooling - deferred indefinitely per [Section 9](https://oraclous.atlassian.net/wiki/spaces/OP/pages/65988)

## Deliverables

- [x] **organisation_id on every storage primitive** - verified by static analysis pass showing no Neo4j label, Postgres table, Redis key prefix, or index name without `organisation_id` scoping
- [x] **Every query path enforces organisation_id** - verified by every Cypher query, Postgres SELECT/UPDATE, Redis GET/SET, and search call routing through a parameterised `organisation_id` sourced from authenticated context, never from request body
- [x] **Multi-tenant components extended** - verified by the three existing multi-tenant retriever wrappers gaining an outer organisation-scoping layer with behaviour preserved for single-organisation deployments
- [x] **Isolation test suite extended** - verified by 100% pass on all existing isolation tests plus new organisation-boundary tests (cross-org read denial, cross-org write denial, cross-org Cypher traversal denial, cross-org search denial, cross-org cache miss). This is the release gate; no deliverable ships until this passes. **Binding acceptance criterion (substrate-level proof):** the organisation-boundary tests must execute against real substrate instances — Neo4j, Postgres, and Redis (testcontainers or equivalent) — and assert denial at the data layer, not at the API/controller layer. A mocked-DB test asserting an HTTP 403 does NOT satisfy this gate: it proves the controller refuses, not that a Cypher traversal, a search call, or a Redis key cannot leak across organisations at the substrate. The test story for this deliverable must stand up real substrate and assert at the data layer; it may not reuse the existing mocked API-403 pattern for the org-boundary assertions.
- [x] **Metering subsystem live** - verified by every metered operation (LLM call, tool invocation, storage write, traversal) producing a metering record with `organisation_id` and `workspace_id`; writes are append-only and tamper-evident; enforced at substrate level, not application level
- [x] **Usage reporting API** - verified by an endpoint returning per-organisation token/invocation/storage/time aggregates over configurable time ranges, ReBAC-gated to organisation admins
- [x] **Migration script for existing deployments** - verified by the script applying cleanly to a staging clone, being idempotent, having a documented rollback path, and adding a seed `organisation_id` to all existing data
- [ ] **Compliance engagement started** - verified by audit firm selected, SOC 2 Type II observation window started, and ISO 27001 scope agreed (R-Compliance release tracks the full compliance work)

## Governance impact

R0.5 makes the Structured Governance Taxonomy bindable. Before this release, the policy sets exist as YAML but have nothing to bind to - `owner_organization` is a concept without a substrate primitive. After this release, every governance policy set can resolve `owner_organization` to a concrete organisation row, and the policy enforcement points named in the taxonomy (substrate, harness load, harness runtime) have a target to evaluate against. R0.5 does not itself enforce any policy set - that begins in R2 at the capability-registry level - but it establishes the tenancy primitive every later enforcement step depends on.

| An agent or operator passes `organisation_id` from the request body, bypassing the authenticated context | Low | Static analysis lint rule rejects any code path that reads `organisation_id` from request body. ## Dependencies

**Upstream:** R0 (the architecture and ADRs that define what tenancy means and why it's at the outermost layer).

**Downstream:** Every release from R1 onward inherits the `organisation_id` scoping at the substrate layer. R3 and R4 in particular must not be started until R0.5 closes; decomposing services without organisation scoping first would require revisiting every service boundary again to add it. R-Compliance depends on R0.5 to begin SOC 2 evidence collection.
