> **This release supersedes the old roadmap.** R2 and R3 (and R2's capability registry) shipped **hollow** — see [R2](r2-phase-2-capability-registry-consolidation.md) and [R3](r3-phase-3-knowledge-graph-decomposition.md). R3.5 rebuilds **every backend service real, end-to-end, per service**, against the legacy behavioural spec. The old [R4](r4-phase-4-harness-runtime-extraction.md)–[R8](r8-phase-8-security-hardening-pass.md) phases and the [gateway-from-R5 vertical-slice plan](revised-plan-gateway-from-r5-fe-be-slices.md) are **discarded**; their surfaces fold into the per-service sequence here.

## Goal

Make **every backend service real and end-to-end** — no stubs, no `raise NotImplementedError`, no dead logic left behind in `oraclous-core-service`. The platform's "done" releases shipped as scaffolding: stub endpoints returning 501, a `GraphNodeService` stub class defined inside a route file, ~6,300 LOC of real ingestion/retrieval/tool logic left **undeleted and dead** in `oraclous-backend/oraclous-core-service/`, and an auth surface that dropped human/email/OAuth and organisation management entirely. R3.5 closes that gap by rebuilding each service to do what the legacy actually did, **per service**, one at a time. A service is not "done" because its PR merged green against stub-tests — it is done only when it runs against real substrate, passes an end-to-end smoke, and **Reza has personally tested it and signed off** before the next dependent service starts. The legacy app is the behavioural specification; the [§21 canonical service architecture](#21-canonical-service-architecture) is the structural target.

The output is a backend where each service is independently real: it builds, runs in `docker compose`, answers `GET /health`, serves real (not stubbed) endpoints against real Neo4j/Postgres/Redis, and has been accepted by a human. Only when the dependency chain is complete does `oraclous-core-service` get salvaged-then-deleted, and only then does the application gateway go up.

## Scope

Strictly sequential, graph-first. Each numbered service is one deliverable; it must reach the [§22 Definition of Done](#22-definition-of-done) (8 gates, including Reza sign-off) before the next dependent service begins. Until the gateway (6) exists, services are reached **directly by host `IP:port`** — legacy parity; the legacy app had no gateway.

### In scope — the per-service sequence (1 → 6)

1. **`knowledge-graph-service` (ingest)** — the write side. Real ingestion end-to-end per the [ADR-022](../adr/adr-022-recipe-primitive-unified-graph-ingestion.md) recipe/primitive/unified-graph model: a data source → primitives → graph, driven by concern-driven recipes rather than per-source code. Schema management, multi-tenant write components, analytics (community detection, centrality). Real Neo4j writes; no stubbed pipeline.
2. **`knowledge-retriever-service` (read)** — the read side, built on (1). Vector / full-text / hybrid / graph-traversal / temporal retrieval, federation traversal, the modality-uniform `NodeResult` envelope — all returning real results from the real graph, read-only Neo4j role. Depends on (1) being accepted (there is nothing to retrieve until ingest is real).
3. **identity / org service (NEW)** — users + email + OAuth (Google / GitHub / Notion) + organisations / members / roles / invites. This is the surface R2/R3 auth **dropped**. Organisations **leave the graph service** and live here. New service, not a lift of the hollow auth stub; legacy auth is the behavioural spec for the human/email/OAuth pieces.
4. **`credential-broker-service`** — real credential storage, scoping, and brokering, depending on (3) for the identity/org it scopes credentials to.
5. **capability-registry + tools + connectors** — port the **real** registry, tool, and connector logic out of `oraclous-core-service` (the ~6,300 dead LOC) into the real `capability-registry-service`, tested against real substrate. **Then** salvage-then-delete `oraclous-core-service` (human-gated; see [hollowness audit & salvage-then-delete](#hollowness-audit--salvage-then-delete)). This is where R2's hollow registry is made real.
6. **`application-gateway`** — the single front door, built last because it has nothing real to front until (1)–(5) exist. Until it ships, callers use host `IP:port` directly. Folds in what the old R6 gateway phase covered.

### Out of scope

* **Frontend** — R3.5 is a backend-realness release; FE is tracked separately ([RF](rf-phase-a-frontend-foundation.md)) and re-sequenced after the gateway (6) is real.
* **New modalities** (image / audio / video) beyond what the legacy ingest/retrieve already did — additive, deferred.
* **The old R7 compiler-harness and R8 security-hardening-pass surfaces** as standalone phases — discarded as phases; any still-needed slice is folded into the owning service above (e.g. security hardening is a per-service gate, not a trailing phase).
* **Writing to `legacy-reference/`** — never. The spec is read with `git show develop:<path>` (see [Spec](#spec)).

## Definition of Done

A **service** is done only when **all 8 gates** pass. A merged PR with green stub-tests satisfies **none** of gates 2–6. Per ORAA-4 §22:

1. **Structurally conformant** — passes [§21](#21-canonical-service-architecture); the `tools/lint/check_service_structure.py` checks (STR001–005) are clean and the per-service import contracts in `pyproject.toml [tool.importlinter]` hold.
2. **Not hollow** — `tools/lint/check_no_stubs.py` returns **zero** findings (HOL001–005) and the service is flipped `claimed_done: true` in `tools/lint/service_status.yaml`.
3. **It runs** — `docker compose up` brings it up **healthy**; `GET /health` returns 200.
4. **Real endpoints** — integration tests run against **real** substrate via testcontainers; no stub, no 501.
5. **End-to-end smoke vs real substrate** — `services/<svc>/tests/smoke/smoke.sh` passes, and runs in CI as the **docker-required `r3_5_gate` job** (modelled on the existing `r2-gate`).
6. **Reza personally tests it and signs off** — the service's issue carries **`needs-human`** until Reza accepts it. **No service is done while `needs-human` is set**, and the next dependent service does not start until sign-off lands.
7. **Merged** — the implementing PR(s) are merged via the gated merge path (ORAA-4 §6).
8. **Handed off** — the run ends by handing the chain to the next service's owner (ORAA-4 §4 / §9.1), or by escalating — never "done, nothing assigned".

The **release** R3.5 is Released only when services 1–6 are each independently at this bar and `oraclous-core-service` has been salvaged-then-deleted under human sign-off.

## Spec

The behavioural specification is the **legacy `develop` branch pinned at commit `84152635de05c105765cfe6b631bb5ba81f2f4aa`** (TASK-237). It is read-only and accessed by `git show develop:<path>` against that commit — **never** by writing to `legacy-reference/`, and never by switching the legacy worktree off `develop`.

The structural and ingestion targets:

* **[§21 canonical service architecture](#21-canonical-service-architecture)** — the layered shape every service adopts (narrative: [engineering/service-architecture-standard.md](../engineering/service-architecture-standard.md)).
* **[ADR-022](../adr/adr-022-recipe-primitive-unified-graph-ingestion.md)** — the recipe / primitive / unified-graph ingestion model that `knowledge-graph-service` (1) implements: any data source becomes a graph via concern-driven recipes, not per-source code.

New code passes when it does what the legacy did at commit `84152635`, **plus** the §21 structural invariants — per the lift-vs-rewrite convention in [09. Releases §7](index.md). "Start from scratch" is the exception (service 3, identity/org) and is justified there.

### §21 Canonical service architecture

Adopted from the legacy app's `app/{core,models,repositories,routes,schema,services}` layout. Package root `services/<svc>/src/oraclous_<svc>_service/` with:

* `main.py` — `app = create_app()` only;
* `app/factory.py` — `create_app` builds + wires + includes routers; **no handlers, no logic**;
* `routes/` — `APIRouter`s; a handler is `parse → ONE service call → HTTP map`;
* `services/` — **all** business logic;
* `domain/` — pure entities, no I/O (optional);
* `repositories/` (+ `models.py`) — the **only** DB / Neo4j / Redis access; ORM lives here;
* `schema/` — Pydantic DTOs only;
* `core/{config,dependencies,lifespan}.py`;
* `migrations/`.
* `tests/{unit,integration,smoke}/` — **not** under `src/`.

**Three non-negotiable rules:** (1) no business logic in route handlers; (2) no non-`BaseModel` class definitions and no DB drivers in `routes/`; (3) repositories are the **only** DB/Neo4j/Redis access (connection setup in `core/lifespan.py` excepted).

**Enforcement** (CI `lint` job + pre-push): `tools/lint/check_service_structure.py` (STR001–005), `tools/lint/check_no_stubs.py` (HOL001–005, gated on the `claimed_done` flag in `tools/lint/service_status.yaml`), and per-service internal import contracts in `pyproject.toml [tool.importlinter]` (`routes → services → domain → repositories → core`). Full narrative: [engineering/service-architecture-standard.md](../engineering/service-architecture-standard.md).

## Hollowness audit & salvage-then-delete

R3.5 begins from an honest map of what actually shipped.

**Hollowness audit.** `tools/audit/hollowness_audit.py` produces a true-completion map across the backend and **re-opens** the hollow R2/R3 "done" stories under R3.5. What it documents:

* stub endpoints and `raise NotImplementedError` in the R2/R3 services;
* a `GraphNodeService` **stub class defined inside a route file** (a §21 rule-2 violation as well as a hollowness one);
* **~6,300 LOC** of real ingestion / retrieval / tool / connector logic left **undeleted and dead** in `oraclous-backend/oraclous-core-service/`;
* the auth surface that dropped **human / email / OAuth / organisation management** — the work now in service (3).

**Salvage-then-delete `oraclous-core-service`.** The ~6,300 LOC is the real spec for service (5). `oraclous-core-service` therefore **stays** — marked `port_source: true`, `deletable: false` — until its logic is **ported into and tested in** `capability-registry-service` (R3.5 step 5). Only then is it deleted. Deletion is **destructive** → it requires **human sign-off** (ORAA-4 §15 destructive-change protocol). No agent auto-deletes it; the salvage must be proven (gates 4–6 on service 5) before the delete is even proposed.

## Anti-micro-ticket (§23)

Per ORAA-4 §23: **one service = one deliverable**, decomposed into **≤ 6 coarse vertical slices**. Each slice cuts **all layers** (route → service → repository), ends in a **passing smoke**, and is a **single `[tests]` + `[impl]` pair**. There is **no** ticket per file, per import, or per endpoint-shell, and no giant interlocked task graph. This is the discipline that stops R3.5 from regenerating the hollow scaffolding R2/R3 produced.

## Governance impact

R3.5 changes what "done" *means*: ORAA-4 §22 makes "merged PR + green stub-tests" satisfy **none** of the realness gates, and forbids any service being marked done while `needs-human` (Reza sign-off) is set. The hollowness audit makes prior "done" claims auditable and re-openable. The `service_status.yaml` `claimed_done` flag becomes the single machine-checked assertion that a service is real, gating `check_no_stubs`.

## Dependencies

**Upstream:** R0 (architecture), R0.5 (tenancy substrate), R1 (auth/credential base). The legacy spec at `develop@84152635`.

**Internal sequence (hard-ordered):** (1) `knowledge-graph-service` → (2) `knowledge-retriever-service` → (3) identity/org → (4) `credential-broker-service` → (5) capability-registry + tools + connectors (then salvage-then-delete `oraclous-core-service`) → (6) `application-gateway`. Each is gated by the prior's Reza sign-off.

**Downstream:** Frontend re-sequencing ([RF](rf-phase-a-frontend-foundation.md)) resumes once the gateway (6) is real. No old R4–R8 release is downstream of R3.5 — they are superseded.
